# Keep Coding for Justice alive without it owning your life

**Plan only.** This page does not authorise invitations, publication, access or
DNS changes. Only the approved maintainer may do routine state changes, and
only the approved rollback authority may make the Site owner-only or apply a
recorded rollback unless an immediate privacy or security emergency requires
the owner to close access.

The site should ask for a small routine, not constant attention. No feed,
notification or backlog is a measure of success.

## Once a week — ten minutes

Pick one fixed time. If it is missed, move the check; do not create seven catch-up
jobs.

1. Open the home page. Is it clear what this is and what someone can do?
2. Open the protected workshop. Do only the one next job it shows.
3. Check that every form meant to be shut is still shut.
4. If a test is open, check its closing date, reply capacity, deletion proof and
   latest automatic-check time. Close invitations if that time is not recent.
5. Check the recent Site errors. One real visitor problem becomes the next job.
6. Leave one short Workshop Note only when something actually changed.

Stop after ten minutes unless the site is unsafe or losing data.

## Once a month — twenty minutes

1. Check the apex and `www` HTTPS certificates and redirect.
2. Check the privacy contact still works and the promised reply time is honest.
3. Check that the owner and deputy can sign in and recover the Sites, GitHub,
   Hover and mailbox accounts. Never put passwords or recovery codes in Git.
4. Run the release check and review dependency updates. Do not update merely to
   clear a badge; update when the change is understood and tested.
5. Check that the database can be inspected and that retention/deletion evidence
   is still being made when expected.
6. Ask: should this repair continue, change, hand over or stop?

## Every release

1. Make one bounded change.
2. Run `npm run verify:release`.
3. Deploy owner-only first and check the exact saved version.
   If the hosted automatic-check time is missing or old, keep invitations shut.
   A private Cloudflare timer test may help find the fault, but its heartbeat is
   not the Site's heartbeat.
4. Record source, version, access, environment-key names, migration and
   content-free row counts in the release packet.
5. Public access or DNS needs its own exact approval. A code change is not that
   approval.
6. Keep the previous Sites version and GitHub rollback source. Never delete the
   database during an ordinary rollback.

## If you are ill, away or fed up

- Stop new invitations and public intake first.
- Stop any direct-reply job, revoke open links and delete full replies promptly.
  Any public result is a separate, public-evidence-only job.
- Put one plain line on the current repair saying work is paused, if publishing
  that line is separately approved.
- If nobody can watch private data within the promised reply time, return the
  Site to owner-only.
- Hand over one repair, one next job and one stop date—not a backlog.

## Minimum people before real participation

| Job                        | Main person | Backup |
| -------------------------- | ----------- | ------ |
| Keep the Site working      | —           | —      |
| Read private replies       | —           | —      |
| Check fairness and consent | —           | —      |
| Answer privacy requests    | —           | —      |
| Approve rollback           | —           | —      |

One person may hold more than one job for a tiny test, but every job needs a
named backup or a clear rule that closes the relevant form.

## What maintenance is not

- It is not chasing views, outrage or daily posts.
- It is not accepting every problem.
- It is not storing private stories in notes, screenshots or AI tools.
- It is not keeping a failed repair alive to avoid embarrassment.
- It is not promising an exact response or deletion time that nobody can meet.

The useful rhythm is: **one repair, one next job, one check date, one person who
can stop it.**
